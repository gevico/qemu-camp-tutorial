# QEMU 训练营项目终期报告

## 一、项目概述

本项目为 QEMU 训练营。虽然项目以 QEMU 命名，但在我看来，QEMU 只是一个切入点——我们以 QEMU 虚拟机为基础，围绕设备虚拟化、GPU 虚拟化等方面进行了更多的探索。

我主要选择的方向是 AI 加速卡建模，以下是对本次项目收获的总结。

## 二、QEMU 虚拟机平台认知

通过本次项目，我加深了对 QEMU 的认识：

- QEMU 是一个开源的虚拟机平台，功能非常强大。
- 与 VMware 不同，VMware 可能只是操作系统层面的虚拟化，而 QEMU 可以对整台机器进行完整定义，包括 PCIe 总线、外设等所有设备。

## 三、GPU 结构学习

在完成专业阶段 17 道题目的过程中，我对 GPU 的结构有了更深入的了解，主要包括：

- block、warp、thread 这几个概念之间的区别；
- GPU 的寄存器体系，从最基本的 device ID，到相对复杂的控制寄存器（如 DMA 寄存器）等。

## 四、GPU AI 建模加速卡项目

### 4.1 项目目标

在 guest 虚拟机中运行 Kimi 2.6 模型，并研究 CXL，HetGPU 等对推理性能的影响。

### 4.2 技术链路

- 在 guest 虚拟机中使用 llama.cpp 将 Kimi 2.6 模型跑起来；
- llama.cpp 的下层是 libcuda，libcuda 的指令通过 CXL server 转发出去；
- 外部有一个 HetGPU 后端，接收到 CXL server 转发过来的指令后，首先将其转译成中间语言，再根据目标架构将中间语言转换成目标架构对应的指令；
- 如果是 NVIDIA 到 NVIDIA 的转换，则直接透传，不会经过"先反编译、再编译"的过程。

## 五、CMB 环境下的开发与持久化方案

在项目开发过程中，我熟悉了一套在 CMB 上进行开发的解决方案：

- **持久化方案**：使用 CMB 的制品库，将编译产物以及磁盘镜像等必要文件打包成 Docker 镜像，推送到制品库中保存；
- **QEMU Lab 支持**：项目会保存三份历史备份，可以随时回滚到过去三份中的任意一份进行恢复。每次打开工作环境时，只需要运行 QEMU Lab 中的 restore 脚本，即可将所有信息恢复；需要更新中间产物时，则使用 save 脚本。

**存在的问题**：

- 目前的持久化方案仍需要手动维护，如果能做到自动备份会更好；
- 制品库的容量有限；
- 备份和拉取的时间非常长，例如 Kimi 模型一共有 232GB，将这类超大规模模型上传到制品库需要相当长的时间。

## 六、大模型文件存储与备份经验

- **Git LFS 存储**：为了保存 Kimi（232GB）这样规模的文件，我们使用 Git LFS（Large File System）。将模型文件上传到 LFS 节点，经过缓存处理后，拉取速度会快很多。
- **断点续传与自动备份**：Concordia 项目提供了下载 Kimi 的脚本，并支持断点续传。但由于 CMB 环境本身的影响，机器会在 17 小时（未加 GPU）或 4 小时（加 GPU）后自动回收开发环境，如果不及时将下载好的模型进行备份，很可能前功尽弃。为此我编写了一个脚本，每隔半小时执行一次 LFS push，推送完成后再继续断点续传，形成"传一次、备份一次"的循环，最大限度保证模型数据的安全。

## 七、子模块（submodule）经验

通过本次项目，我了解了 submodule 机制：

- 我们的项目包含非常多的子仓库，例如 CXL memory server 项目中集成了 CUDA 子项目，Concordia 中也集成了 NVIDIA 相关的子项目；
- 子模块不参与 git 追踪：如果对子项目进行了修改，但不单独对该子仓库进行 push，修改内容不会随着上层项目仓库的更新而更新。子模块是一个独立的模块，需要单独维护。

## 八、AI 建模加速卡的两套流程与当前进展

对于 AI 建模加速卡，目前有两套流程：

**流程一（试验流程）：Concordia 跑通**

- 在 host 机器上运行 llama.cpp，并在其上运行 Kimi 模型；
- 将指令直接发送给 Concordia（即 HetGPU 的后端），由后端进行指令的反编译和编译；
- 如果这一流程成功，说明 run_kimi 脚本可以跑出 TPS 数据。

**流程二（完整链路）：模型放入虚拟机**

- 将模型放入虚拟机中，走完整的 CXL server 链路；
- 这一部分我尚未完全跑通，但已经基本达到在 QEMU 中把 llama.cpp 跑起来的状态。
